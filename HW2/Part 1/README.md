# تمرین HTTP — مهندسی اینترنت

## سؤال ۱: نسخه‌های مختلف HTTP

تفاوت‌های اصلی نسخه‌های HTTP به‌صورت کلیدواژه‌ای:

- **HTTP/0.9:** فقط `GET`، پاسخ صرفاً HTML، بدون Header و Status Code، اتصال جداگانه برای هر درخواست.
- **HTTP/1.0:** اضافه‌شدن Header، Status Code و متدهای دیگر مثل `POST` و `HEAD`، پشتیبانی از انواع محتوا، اتصال غیرماندگار به‌صورت پیش‌فرض.
- **HTTP/1.1:** اتصال ماندگار (`Keep-Alive`) به‌صورت پیش‌فرض، `Host` Header، قابلیت `Pipelining`، انتقال قطعه‌ای (`Chunked Transfer Encoding`) و بهبود Cache.
- **HTTP/2:** انتقال باینری، چندجریانی (`Multiplexing`) روی یک اتصال TCP، فشرده‌سازی Header با `HPACK` و کاهش سربار درخواست‌ها.
- **HTTP/3:** استفاده از `QUIC` روی UDP به‌جای TCP، چندجریانی مستقل، راه‌اندازی سریع‌تر اتصال و کاهش مشکل `Head-of-Line Blocking` بین جریان‌ها.

**علت استفاده از UDP در HTTP/3:** در HTTP/2، با اینکه چند درخواست هم‌زمان روی یک اتصال TCP ارسال می‌شوند، گم‌شدن یک بسته می‌تواند تحویل داده‌های سایر جریان‌ها را هم متوقف کند. HTTP/3 با استفاده از QUIC روی UDP، قابلیت‌هایی مثل ارسال قابل‌اعتماد، کنترل ازدحام، رمزنگاری و مدیریت جریان‌ها را در خود QUIC پیاده می‌کند. در نتیجه، گم‌شدن بسته در یک جریان لزوماً سایر جریان‌ها را متوقف نمی‌کند و اتصال هم سریع‌تر برقرار می‌شود. بنابراین HTTP/3 از UDP برای حذف این محدودیت‌های TCP استفاده کرده، نه برای کنار گذاشتن قابلیت اطمینان.

## سؤال ۲: Stateful و Stateless

**الف)** در ارتباطات `Stateless`، هر درخواست مستقل از درخواست‌های قبلی پردازش می‌شود و سرور برای فهم درخواست فعلی به نگهداری وضعیت ارتباط قبلی وابسته نیست. در مقابل، در ارتباطات `Stateful`، وضعیت تعامل کاربر یا ارتباط در طول چند درخواست نگهداری می‌شود و درخواست‌های بعدی می‌توانند به اطلاعات قبلی وابسته باشند. برای مثال، در یک ارتباط Stateful ممکن است سرور وضعیت یک نشست فعال را ذخیره کند، ولی در حالت Stateless اطلاعات لازم باید همراه هر درخواست ارسال شود.

**ب)** پروتکل HTTP ذاتاً `Stateless` است؛ یعنی سرور صرفاً از روی پروتکل نمی‌فهمد دو درخواست متعلق به یک کاربر یا یک نشست هستند. برای حفظ وضعیت در برنامه‌های وب از روش‌هایی مثل `Cookie` و `Session` استفاده می‌شود. معمولاً یک شناسه نشست در Cookie مرورگر ذخیره می‌شود و سرور با استفاده از آن اطلاعات نشست را پیدا می‌کند. روش دیگر استفاده از `Token` مانند JWT است که کلاینت آن را همراه درخواست‌های بعدی ارسال می‌کند. این روش‌ها امکان حفظ وضعیت در سطح برنامه را فراهم می‌کنند، بدون اینکه ماهیت HTTP تغییر کند.

## سؤال ۳: محدودیت مدل Client/Server

**الف)** در الگوی معمول HTTP، کلاینت درخواست می‌فرستد و سرور به آن پاسخ می‌دهد. بنابراین اگر اتفاق جدیدی در سرور رخ دهد، سرور در حالت عادی نمی‌تواند بدون وجود درخواست یا ارتباطی که از قبل برقرار شده، مستقیماً یک پاسخ HTTP جدید برای مرورگر ارسال کند. این موضوع برای پیام‌رسانی، اعلان‌های لحظه‌ای و نمایش تغییرات زنده چالش ایجاد می‌کند، چون ممکن است داده جدید آماده باشد ولی کلاینت هنوز از آن خبر نداشته باشد.

**ب) راهکارها:**

**۱. Polling:** کلاینت در فاصله‌های زمانی مشخص، مثلاً هر چند ثانیه، یک درخواست HTTP به سرور ارسال می‌کند تا وجود اطلاعات جدید را بررسی کند. پیاده‌سازی این روش ساده است و با HTTP معمولی کار می‌کند، اما اگر داده‌ای تغییر نکرده باشد درخواست‌های اضافی تولید می‌شود. همچنین ممکن است بین ایجاد یک رویداد و دریافت آن تا اندازه فاصله دو درخواست تأخیر وجود داشته باشد.

**۲. Long Polling:** کلاینت درخواست را ارسال می‌کند، اما سرور در صورت نداشتن اطلاعات جدید، پاسخ را بلافاصله برنمی‌گرداند و درخواست را تا زمان وقوع رویداد یا پایان مهلت مشخص باز نگه می‌دارد. پس از دریافت پاسخ، کلاینت درخواست تازه‌ای ارسال می‌کند. این روش در مقایسه با Polling معمولی تأخیر و درخواست‌های بیهوده کمتری دارد، ولی همچنان به مدیریت درخواست‌های معلق و ایجاد مجدد آن‌ها نیاز دارد.

**۳. Server-Sent Events (SSE):** کلاینت یک اتصال HTTP به سرور برقرار می‌کند و سرور با باز نگه داشتن پاسخ، رویدادهای جدید را به‌تدریج در همان اتصال ارسال می‌کند. این روش برای اعلان‌ها، نمایش پیشرفت عملیات و به‌روزرسانی زنده مناسب است. ارتباط SSE یک‌طرفه و از سرور به کلاینت است؛ برای ارسال اطلاعات از کلاینت به سرور باید از درخواست HTTP دیگری استفاده شود.

**۴. WebSocket:** ابتدا ارتباط با یک Handshake آغاز می‌شود و سپس یک کانال ارتباطی پایدار و دوطرفه ایجاد می‌شود. در این حالت هم کلاینت و هم سرور می‌توانند بدون ارسال درخواست HTTP جدید برای هر پیام، داده بفرستند. به همین دلیل WebSocket برای چت و بازی‌های آنلاین مناسب است. البته نگهداری اتصال‌های باز و مدیریت قطع و وصل شدن آن‌ها نسبت به درخواست‌های عادی HTTP پیچیدگی بیشتری دارد.

**۵. Webhook:** در ارتباط بین دو سرویس، سرویس دریافت‌کننده یک آدرس HTTP در اختیار سرویس ارسال‌کننده قرار می‌دهد. وقتی رویداد مشخصی اتفاق بیفتد، سرویس ارسال‌کننده یک درخواست HTTP (معمولاً `POST`) به آن آدرس می‌فرستد. بنابراین نیازی نیست سرویس دریافت‌کننده مدام وضعیت رویداد را بررسی کند. در واقع محدودیت آغاز ارتباط حذف نشده است؛ فقط سرویس تولیدکننده رویداد برای ارسال اعلان، نقش کلاینت را بر عهده می‌گیرد. این روش برای اعلان پرداخت یا تغییر وضعیت سفارش کاربرد دارد.

## سؤال ۴: اجزای URL

آدرس داده‌شده:

`ss://asghar:1234!!@ss.myproxy.com:1234#shadowSocks1`

| بخش | مقدار | توضیح |
|---|---|---|
| Scheme | `ss` | طرح آدرس‌دهی مربوط به Shadowsocks |
| Userinfo | `asghar:1234!!` | اطلاعات قبل از علامت `@` |
| Method | `asghar` | نام روش رمزنگاری در قالب متنی Shadowsocks |
| Password | `1234!!` | گذرواژه اتصال |
| Host | `ss.myproxy.com` | نام دامنه سرور |
| Port | `1234` | شماره پورت سرور |
| Fragment / Tag | `shadowSocks1` | برچسب یا نام نمایشی اتصال |

در این آدرس Path و Query وجود ندارد. همچنین `ss` به معنای `https` نیست و این لینک، آدرس یک اتصال Shadowsocks است. مقدار `asghar` از نظر جایگاه نقش Method را دارد، ولی لزوماً نام یک الگوریتم رمزنگاری معتبر نیست.

## سؤال ۵: کدهای وضعیت HTTP

**۱. خرابی دیتابیس و انجام نشدن درخواست‌های ورود:** کد **`503 Service Unavailable`** مناسب است، چون سرویس به علت وابستگی به دیتابیس فعلاً قادر به پاسخ‌گویی نیست. اگر خرابی غیرمنتظره‌ای در برنامه رخ داده باشد، `500 Internal Server Error` هم قابل‌استفاده است، ولی `503` در این سناریو دقیق‌تر است.

**۲. وجود نداشتن نام کاربری و ناموفق بودن ورود:** کد **`401 Unauthorized`** مناسب است، چون اطلاعات احراز هویت ارائه‌شده معتبر نیست. بهتر است برای نام کاربری ناموجود و رمز عبور اشتباه پاسخ یکسانی داده شود تا امکان تشخیص حساب‌های ثبت‌شده برای مهاجم کمتر شود.

**۳. انتقال وب‌سایت به دامنه دیگر:** کد **`301 Moved Permanently`** مناسب است، چون آدرس وب‌سایت به‌صورت دائمی عوض شده است و آدرس جدید در Header به نام `Location` قرار می‌گیرد. کد `308 Permanent Redirect` نیز در صورت نیاز به حفظ متد و بدنه درخواست هنگام Redirect گزینه مناسبی است.

**۴. بیشتر بودن تعداد درخواست‌ها از نرخ مجاز:** کد **`429 Too Many Requests`** مناسب است، چون کاربر محدودیت نرخ درخواست (`Rate Limit`) را رد کرده است. سرور می‌تواند با Header به نام `Retry-After` زمان مناسب برای تلاش مجدد را اعلام کند.

**۵. تمدید موفق JWT و بازگرداندن توکن در Header:** کد **`200 OK`** مناسب است، چون عملیات موفق بوده است. اگر پاسخ هیچ بدنه‌ای نداشته باشد و توکن جدید فقط در Header قرار گیرد، **`204 No Content`** نیز انتخاب دقیقی است.

**۶. درخواست از محدوده IP ممنوع:** کد **`403 Forbidden`** مناسب است، چون سرور درخواست را دریافت و متوجه شده، اما طبق سیاست دسترسی اجازه ارائه سرویس به این IP را نمی‌دهد. کد `451 Unavailable For Legal Reasons` تنها زمانی مناسب‌تر است که محدودیت واقعاً به علت یک الزام قانونی اعمال شده باشد.

## سؤال ۶: انواع Proxy

**۱. دریافت پکیج‌ها از سرور داخلی دانشگاه:** **Caching Proxy (یا Repository Mirror)**؛ درخواست دریافت پکیج‌ها از یک سرور داخلی پاسخ داده می‌شود تا نیاز به دانلود مکرر از سرورهای بیرونی کمتر شود. اگر سرور دانشگاه خودش مخزن همگام‌شده‌ای از پکیج‌ها باشد، اصطلاح دقیق‌تر `Repository Mirror` است؛ اگر درخواست‌ها را واسطه‌گری و پاسخ‌ها را ذخیره کند، `Caching Forward Proxy` محسوب می‌شود.

**۲. تقسیم درخواست‌ها بر اساس مبدأ جغرافیایی:** **Reverse Proxy / Geo-based Load Balancer**؛ این واسطه مقابل سرورها قرار می‌گیرد و با توجه به موقعیت جغرافیایی IP مبدأ، درخواست را به سرور یا مرکز داده مناسب هدایت می‌کند. هدف می‌تواند کاهش تأخیر یا توزیع بار باشد.

**۳. اضافه کردن احراز هویت به یک سرویس قدیمی:** **Reverse Proxy (Authentication Proxy)**؛ این واسطه پیش از رسیدن درخواست به سرویس قدیمی، هویت و مجوز کاربر را بررسی می‌کند و فقط درخواست‌های مجاز را عبور می‌دهد. بنابراین بدون تغییر اساسی در کد سرویس قدیمی می‌توان لایه احراز هویت به آن اضافه کرد.
