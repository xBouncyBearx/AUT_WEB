# پاسخ تمرین Git

## سؤال ۱: `merge` و `rebase`

دستور `git merge` تغییرات دو شاخه را با هم ترکیب می‌کند. اگر شاخه‌ها از یکدیگر جدا شده باشند، معمولاً یک **merge commit** جدید ایجاد می‌شود که دو والد دارد. بنابراین تاریخچهٔ هر دو شاخه و محل ادغام آن‌ها حفظ می‌شود. اگر امکان **fast-forward** وجود داشته باشد، Git می‌تواند بدون ایجاد merge commit فقط اشاره‌گر شاخه را جلو ببرد.

دستور `git rebase` کامیت‌های اختصاصی یک شاخه را روی آخرین کامیت شاخهٔ مبنا دوباره اعمال می‌کند. به این ترتیب تاریخچه معمولاً خطی می‌شود، اما چون کامیت‌ها دوباره ساخته می‌شوند، شناسهٔ آن‌ها تغییر می‌کند. در هر دو روش ممکن است conflict رخ دهد.

برای ادغام یک شاخهٔ تکمیل‌شده در `main`، مخصوصاً وقتی تاریخچهٔ همکاری اعضای تیم مهم است، `merge` مناسب است:

</div>

```bash
git switch main
git merge feature
```

<div dir="rtl">

اما برای به‌روز کردن شاخهٔ شخصی `feature` با تغییرات جدید `main` پیش از ادغام، `rebase` مناسب است؛ چون تاریخچهٔ شاخه را مرتب‌تر و خطی می‌کند:

</div>

```bash
git switch feature
git rebase main
```

<div dir="rtl">

روی شاخه‌های مشترکی که دیگران کامیت‌هایشان را دریافت کرده‌اند، معمولاً `rebase` انجام نمی‌دهیم؛ چون بازنویسی تاریخچه می‌تواند کار سایر اعضا را مختل کند.

## سؤال ۲: انتخاب بخشی از تغییرات

در خروجی `git diff`، هر **hunk** یک بخش از تغییرات فایل است که معمولاً شامل چند خط تغییرکرده و تعدادی خط اطراف آن‌ها برای مشخص شدن محل تغییر است. ممکن است یک فایل چند hunk جدا داشته باشد.

برای بررسی تغییرات فایل و انتخاب تعاملی بخش‌هایی که باید وارد staging شوند:

</div>

```bash
git diff -- file.txt
git add -p -- file.txt
```

<div dir="rtl">

در حالت تعاملی، Git هر hunk را نشان می‌دهد و از ما می‌پرسد چه کاری انجام شود. گزینه‌های مهم عبارت‌اند از:

- `y`: همین hunk وارد staging شود.
- `n`: این hunk وارد staging نشود.
- `s`: در صورت امکان، hunk به بخش‌های کوچک‌تر تقسیم شود.
- `e`: patch به‌صورت دستی ویرایش شود تا قسمت دقیق‌تری انتخاب کنیم.
- `q`: خروج از انتخاب تعاملی.
- `?`: نمایش راهنمای گزینه‌ها.

پس از انتخاب، با دستورهای زیر بخش‌های staged و unstaged را جداگانه بررسی می‌کنیم:

</div>

```bash
git diff --cached -- file.txt
git diff -- file.txt
git commit -m "Update selected parts of file"
```

<div dir="rtl">

این روش باعث می‌شود تغییرات نامرتبط را در یک کامیت قرار ندهیم؛ مثلاً اصلاح یک باگ را جدا از تغییر ظاهر کد ثبت کنیم. در نتیجه هر کامیت هدف مشخصی دارد و بررسی یا بازگرداندن آن آسان‌تر می‌شود. تغییراتی که انتخاب نشده‌اند در working tree باقی می‌مانند.

## سؤال ۳: یافتن منشأ خطا با `git bisect`

دستور `git bisect` برای پیدا کردن کامیتی استفاده می‌شود که یک خطا را وارد پروژه کرده است. این ابزار با روش **جست‌وجوی دودویی**، به‌جای بررسی تک‌تک کامیت‌ها، هر بار تقریباً نیمی از محدودهٔ جست‌وجو را کنار می‌گذارد.

ابتدا یک کامیت معیوب (`bad`) و یک کامیت قدیمی‌تر که مطمئنیم سالم بوده (`good`) مشخص می‌کنیم:

</div>

```bash
git bisect start
git bisect bad HEAD
git bisect good <good-commit-hash>
```

<div dir="rtl">

Git یک کامیت میانی را checkout می‌کند. پروژه را در همان وضعیت آزمایش می‌کنیم؛ اگر خطا وجود داشت، آن را `bad` و اگر درست کار می‌کرد، `good` اعلام می‌کنیم:

</div>

```bash
git bisect bad    # اگر خطا وجود دارد
git bisect good   # اگر خطا وجود ندارد
```

<div dir="rtl">

این کار را برای کامیت‌های بعدی که Git انتخاب می‌کند تکرار می‌کنیم تا اولین کامیت معیوب مشخص شود. در پایان با دستور زیر به شاخهٔ قبلی برمی‌گردیم:

</div>

```bash
git bisect reset
```

<div dir="rtl">

مثلاً فرض کنیم بعد از چندین تغییر، صفحهٔ ورود دیگر درست کار نمی‌کند، ولی می‌دانیم دو هفته قبل سالم بوده است. با انتخاب آخرین نسخه به‌عنوان `bad` و نسخهٔ سالم دو هفته قبل به‌عنوان `good` می‌توانیم منشأ خطا را پیدا کنیم. اگر بین آن‌ها ۶۴ کامیت باشد، در حالت معمول تقریباً با ۶ آزمایش به نتیجه می‌رسیم؛ به همین دلیل این روش از بررسی خطی کامیت‌ها سریع‌تر است.

## سؤال ۴: بررسی تغییرات پیش از کامیت

### ۱. بررسی وضعیت و تفاوت تغییرات

</div>

```bash
git status
git diff -- README.md
git diff --staged -- README.md
```

<div dir="rtl">

`git status` وضعیت فایل‌های staged، unstaged و untracked را نشان می‌دهد. `git diff -- README.md` تغییراتی را نمایش می‌دهد که در working tree هستند ولی هنوز وارد staging نشده‌اند. در مقابل، `git diff --staged -- README.md` تغییرات موجود در staging نسبت به آخرین کامیت را نمایش می‌دهد؛ یعنی محتوایی که برای کامیت بعدی آماده است. گزینهٔ `--cached` هم معادل `--staged` است.

### ۲. نتیجهٔ ثبت کامیت معمولی

</div>

```bash
git commit -m "Update README"
```

<div dir="rtl">

چون دستور `git add` را پس از ویرایش دوم تکرار نکرده‌ایم، فقط نسخه‌ای از تغییرات `README.md` که قبلاً staged شده بود در کامیت قرار می‌گیرد. تغییرات بعدی فایل در working tree باقی می‌مانند و کامیت نمی‌شوند. فایل‌های untracked پوشهٔ `tmp/` هم در این کامیت وارد نمی‌شوند.

### ۳. جلوگیری از اضافه شدن فایل‌های موقت

در فایل `.gitignore` در ریشهٔ مخزن، خط زیر را قرار می‌دهیم:

</div>

```gitignore
/tmp/
```

<div dir="rtl">

این الگو باعث می‌شود Git فایل‌های untracked داخل پوشهٔ `tmp/` در ریشهٔ مخزن را نادیده بگیرد. اما `.gitignore` روی فایل‌هایی که قبلاً tracked شده‌اند اثری ندارد. برای خارج کردن فایل tracked از index بدون حذف نسخهٔ محلی آن می‌توان از دستور زیر استفاده کرد و سپس این تغییر را کامیت کرد:

</div>

```bash
git rm --cached -- path/to/tracked-file
```

<div dir="rtl">

## سؤال ۵: رفع `merge conflict` در کار گروهی

### ۱. علت conflict

هر دو نفر از یک کامیت مشترک شروع کرده‌اند و یک خط از `README.md` را به دو شکل متفاوت تغییر داده‌اند. Git نمی‌تواند با اطمینان تصمیم بگیرد کدام متن باید در خروجی نهایی باقی بماند؛ بنابراین conflict رخ می‌دهد. البته هر تغییری در یک فایل لزوماً conflict ایجاد نمی‌کند؛ مثلاً اگر افراد قسمت‌های مستقل و غیرهم‌پوشان را ویرایش کنند، Git معمولاً می‌تواند آن‌ها را خودکار ادغام کند.

### ۲. شناسایی conflict و نسخه‌های متن

پس از تلاش برای ادغام:

</div>

```bash
git switch main
git merge feature-description
git status
```

<div dir="rtl">

`git status` فایل‌های دارای conflict را در بخش unmerged paths مشخص می‌کند. همچنین می‌توان نام آن‌ها را با `git diff --name-only --diff-filter=U` دید. داخل `README.md`، به‌طور پیش‌فرض نشانگرهای زیر ظاهر می‌شوند:

</div>

```text
<<<<<<< HEAD
متن موجود در main
=======
متن موجود در feature-description
>>>>>>> feature-description
```

<div dir="rtl">

`<<<<<<< HEAD` آغاز بخش متعلق به شاخهٔ فعلی (`main`) را مشخص می‌کند؛ `=======` دو نسخه را جدا می‌کند و `>>>>>>> feature-description` انتهای متن مربوط به شاخهٔ ورودی را نشان می‌دهد.

### ۳. حفظ هر دو تغییر و تکمیل merge

ابتدا فایل را باز می‌کنیم و متن نهایی را طوری می‌نویسیم که اطلاعات مفید هر دو نسخه حفظ شود؛ سپس همهٔ نشانگرهای conflict (`<<<<<<<`، `=======` و `>>>>>>>`) را از بخش درگیر حذف می‌کنیم. برای بررسی و تکمیل ادغام:

</div>

```bash
git diff --check
git diff -- README.md
git add README.md
git diff --cached --check
git status
git merge --continue
```

<div dir="rtl">

پیش از `git add` فایل را هم دستی بررسی می‌کنیم تا مطمئن شویم هیچ‌کدام از نشانگرها باقی نمانده‌اند؛ چون `git diff --check` به‌تنهایی تضمین نمی‌کند که تمام نشانگرهای conflict حذف شده‌اند. اگر `git status` دیگر مسیر unmerged نشان ندهد و فایل نهایی درست باشد، `git merge --continue` یک merge commit می‌سازد (در صورت باز شدن ویرایشگر، پیام کامیت را تأیید می‌کنیم).

### ۴. لغو merge

اگر تصمیم بگیریم فعلاً ادغام انجام نشود، با فرض وضعیت clean اولیهٔ سؤال دستور زیر مناسب است:

</div>

```bash
git merge --abort
```

<div dir="rtl">

این دستور ادغام در حال انجام را لغو می‌کند و وضعیت قبل از شروع merge را بازیابی می‌کند.

## سؤال ۶: انتخاب روش مناسب برای بازگرداندن تغییرات

### ۱. کنار گذاشتن تغییرات unstaged یک فایل

</div>

```bash
git restore -- notes.txt
```

<div dir="rtl">

این دستور فقط فایل `notes.txt` را در working tree به نسخهٔ staging برمی‌گرداند. طبق فرض سؤال، staging با آخرین کامیت یکسان است؛ پس فایل به وضعیت آخرین کامیت برمی‌گردد. staging، تاریخچهٔ کامیت‌ها و فایل‌های دیگر تغییر نمی‌کنند. تغییرات محلی کنارگذاشته‌شده ممکن است قابل بازیابی نباشند.

### ۲. خارج کردن فایل از staging و حفظ ویرایش‌ها

</div>

```bash
git restore --staged -- notes.txt
```

<div dir="rtl">

این دستور نسخهٔ `notes.txt` در staging را به محتوای `HEAD` برمی‌گرداند؛ اما working tree را تغییر نمی‌دهد. بنابراین ویرایش‌های فایل حفظ می‌شوند و فقط دیگر برای کامیت آماده نیستند. تاریخچهٔ کامیت‌ها هم تغییر نمی‌کند.

### ۳. خنثی کردن کامیت pushشده در شاخهٔ مشترک

</div>

```bash
git switch main
git revert <bad-commit-hash>
git push origin main
```

<div dir="rtl">

`git revert` یک کامیت جدید ایجاد می‌کند که اثر تغییرات کامیت اشتباه را خنثی می‌کند، بدون اینکه آن کامیت را از تاریخچه حذف کند. در نتیجه، پس از انجام موفق revert، محتوای فایل‌های مربوط در working tree و staging با نتیجهٔ کامیت جدید هماهنگ می‌شود و تاریخچه شامل هر دو کامیت اصلی و بازگرداننده خواهد بود. اگر کامیت اشتباه، آخرین کامیت باشد، می‌توان از `git revert HEAD` هم استفاده کرد.

استفاده از `git reset` برای حذف کامیت و سپس `force push` در این حالت مناسب نیست؛ چون دیگر اعضای تیم کامیت قبلی را دریافت کرده‌اند. بازنویسی تاریخچهٔ مشترک می‌تواند باعث واگرایی شاخه‌ها، اختلال در pull و از بین رفتن تغییرات دیگران شود. `revert` تاریخچه را حفظ می‌کند و برای شاخهٔ مشترک امن‌تر است.
